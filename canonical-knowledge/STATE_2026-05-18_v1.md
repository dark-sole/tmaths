# STATE 2026-05-18 v1 — tokenisys-libs-prod / Solidity math libraries

Scope: `tokenisys-libs-prod/solidity`. Foundry math-library test campaign on the

the Canton product suite (Apex, P100, Tokenisys); shares no code path with it.

## What shipped this session

Four bugs found and fixed. Full suite: 124 tests, 124 passing, 0 failing.

1. **`ln` divisor, x1000 error (library bug).** The `ln` Horner final divisor
   literal was `2520000000000000000` (19 digits, 2520e15) but must be
   `2520000000000000000000` (22 digits, 2520e18). `ln` returned values 1000x
   too large with 2^256 wraparounds. Fixed all four occurrences (two per file,
   add-branch `sdiv` and sub-branch `div`) in `TMathFusaka.sol` and
   `TMathLegacy.sol`. Verified against all 21 `LnDebug` outputs: every value
   within 2e-4 relative. Equivalence tests had passed while `ln` was 1000x
   wrong because both libraries shared the identical bug; the mpmath vector
   tier caught it.

2. **trig zero-crossing test tolerance (test bug).** sin/cos vector tests failed
   at true zero-crossings because the mpmath generator emits tiny nonzero
   integers there, and `_relError` divides by `expected`. Added
   `TRIG_ZERO_FLOOR = 1e9` to `TMathVectors.t.sol` and changed the magnitude
   guard from `== 0` to `< TRIG_ZERO_FLOOR` in the four trig vector tests only.
   The two `ln` guards left as `== 0`.

3. **exp reciprocal-identity fuzz bound (test bug).** `testFuzz_Prop_Exp_-
   ReciprocalIdentity` bound `[1e15, EXP_MAX=61e18]` drove `exp(-x)` into a
   regime where the WAD-scaled value has too few significant digits for the
   identity to hold. Capped at `30e18` in `TMathProperties.t.sol`. `EXP_MAX`
   retained, still used by the monotonicity fuzz and revert test.

4. **trig octant wraparound for x >= 2*PI (library bug).** The `trig` octant
   index `r_x` was not reduced modulo 8. For `x >= 2*PI` the raw index runs to
   9, 13, 17; the single `if gt(r_x,4){sub 4}` left it out of range, so the
   sign mask shifted past its 8-bit pattern and the layout/taylor selection
   picked the wrong series — `cos(7.0)`, `cos(10.0)`, `cos(4*PI)` returned the
   `sin` value with wrong sign. Fixed by inserting
   `r_x := add(mod(sub(r_x, 1), 8), 1)` after `theta` is computed and before
   the sign mask, in both files. Verified: all 17 sin and 17 cos vector signs
   correct; behaviour unchanged for `x < 2*PI` (mod-8 and the old single -4
   are identical for raw `r_x` in 1..8). This bug predates the chain split —
   carried over unchanged from the original `TMaths.sol`, which still has it.

5. **`tan` pole division (library bug, exposed by fix 4).** `tan` did
   `result = (sinVal * 1e18) / cosVal` with no guard. With `cos` corrected to
   return true zero at poles (odd multiples of PI/2), `tan` divided by zero —
   EVM panic 0x12. Added `error Undefined()` and `if (cosVal == 0) revert
   Undefined();` to `tan` in both files. `testFuzz_Equiv_Tan` rewritten to
   assert revert-parity (both libraries revert together at poles, or both
   return equal values) via try/catch.
